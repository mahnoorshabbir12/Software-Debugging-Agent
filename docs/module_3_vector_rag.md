# Module 3: Embeddings & Vector RAG

This document logs our learnings from Module 3, where we connected our structured code chunks to an AI semantic retrieval pipeline.

## 1. Embeddings

**What is the concept?**
Embeddings are mathematical vectors (lists of floating-point numbers) generated by AI models. They represent the *semantic meaning* of a piece of text or code, rather than the raw characters.

**What problem does it solve?**
If a developer asks an agent: "Where is user authorization handled?", a standard `grep` search will fail if the codebase uses the term `verify_jwt_token` instead of "user authorization". Embeddings solve this because the AI knows that "authorization" and "JWT token" map to a very similar point in mathematical space.

**Where it is used:** `ingestion/embedder.py`

**Alternative Models:**
- **Cloud Models (OpenAI, Gemini):** Powerful but require sending proprietary codebase data to third-party servers and cost money.
- **Local Models (`sentence-transformers`):** Free, run locally ensuring 100% privacy.

**Why we chose `sentence-transformers`:**
For our debugging agent, we want to allow developers to search their codebase securely and inexpensively on their local machine. `sentence-transformers` provides access to fast, open-source models like `all-MiniLM-L6-v2` that are small enough to run on CPUs but smart enough to understand code context.

## 2. Vector Databases

**What is the concept?**
A database specifically engineered to store vectors alongside payload metadata, utilizing algorithms like HNSW to perform lightning-fast similarity searches across millions of records.

**What problem does it solve?**
Without a vector database, finding the closest match to a query requires calculating the Cosine Similarity against *every single chunk* in a regular Python list (O(N) time). Vector databases do this in milliseconds (O(log N)). Furthermore, they allow us to attach payload data (our `CodeChunk` fields like `file_path` and `symbol`) so we can filter searches (e.g. "Only search in python files").

**Where it is used:** `ingestion/indexer.py`

**Why we chose Qdrant:**
Qdrant is written in Rust (extremely fast), supports complex payload filtering natively, and perfectly balances local development and production scale. Crucially, Qdrant allows us to run entirely in local file mode (saving to a `.qdrant_data` folder) when Docker isn't available, preventing friction during local development.

## 3. The Search Flow

1. The user inputs a natural language query via the CLI (`debugger search "query"`).
2. The `Embedder` turns the string into a 384-dimensional vector.
3. The `Indexer` queries Qdrant for the `top_k` vectors in the `code_chunks` collection with the highest Cosine Similarity to the query vector.
4. Qdrant returns the exact file paths and source code for the agent to read.
