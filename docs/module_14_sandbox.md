# Module 14: Docker Sandbox & Code Execution

This module focuses on executing untrusted AI-generated code safely without risking the host machine's security or stability.

## Concepts Learned

### 1. Container Isolation
**What it is:** Using Docker containers to create a virtualized filesystem and process space. The container runs an OS (e.g. Debian/Alpine) but shares the host machine's kernel.
**What problem it solves:** Executing AI code directly on a host machine could lead to accidental deletion of files or corruption of the environment. Containers provide a safe, disposable environment where code can run and then be destroyed.
**Why we used it here:** To test if the patch successfully fixes the code, we must actually run it. Docker provides the safest way to do this.

### 2. Resource Limits & Network Isolation
**What it is:** Passing flags like `mem_limit='512m'` and `network_mode='none'` when booting a container.
**What problem it solves:** Even in a container, a malicious or buggy script with an infinite loop could consume 100% of the host CPU and memory, effectively causing a Denial of Service (DoS) attack on the user's machine. Furthermore, internet access could allow exfiltration of data.
**Why we used it here:** We explicitly locked down memory and CPU, and completely severed the container's network connection to the outside world, guaranteeing that even the most broken AI script cannot harm the user.

## Transferable Rules
> **Never Trust AI Code:** When building systems that execute code generated by an LLM, always assume the code is malicious or highly buggy. 
> 
> **Use Strict Boundaries:** Always enforce CPU limits, memory limits, timeouts, and network disablement in your sandboxes. A container without these limits is trivial to escape or abuse.
